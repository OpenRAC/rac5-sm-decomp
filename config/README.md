# Configuration layout

This directory holds the measured configuration the tools and the gates read.
It follows the conventions of the OpenRAC RAC1 decompilation
(`rac1-decomp/config/`): one file per question, line-oriented, comments with
`#`, and no configuration that a tool does not read.

| question | file here | RAC1 counterpart | notes |
| --- | --- | --- | --- |
| What exactly is the disc input? | `target.json` | `splat.yaml` (segments) | we pin one boot executable and one USA disc |
| Where are the code spans? | `boot/code_intervals.tsv` | `text.objects`, `core_text.objects` | generated next-label bounds, not function sizes |
| What are the symbols? | `boot/symbols.tsv` | `symbol_addrs.txt`, `symbol_names.txt` | one table, `.text`/`.data`/`.bss` in a column |
| What did a body compile to? | `boot/witness_boundaries.tsv` | — | generated witness extents, body plus alignment |
| Which chain builds each source? | `cflags.txt` | `file_cflags.txt` | ours also names the compiler driver and the assembler |
| Which toolchain is pinned? | `boot/compiler_trial.json`, `levels/compiler_trial.json` | `Makefile.sn` flags | hashes, provenance and source patches per selector |
| Which level modules exist? | `levels/modules.tsv` | `overlays/` | twenty numbered modules plus the frontend |
| Which bodies are known assembly? | `handwritten_asm.tsv` | `handwritten_asm.txt` | a measured verdict per function, with the wave that measured it |
| What is the boot load image? | `boot/elf_layout.json`, `boot/dvp_overlays.tsv` | — | measured layout and the non-loaded DVP catalogue |
| What are the accepted level C bodies? | `levels/bodies.tsv` (schema below) | per-overlay sources | one row per placement; the source's own facts live in `levels/body_sources.tsv` |
| Which compiler-generated local calls are qualified? | `levels/local_link_symbols.tsv` | — | a reviewed module/source/object and helper fingerprint for a specific call-site set |
| Which level functions are copies of named boot functions? | `levels/function_names.tsv` | `symbol_addrs.txt` | generated by `tools/level_function_names.py`: module, offset, size, boot symbol and address |
| Which original source file does level code come from? | `levels/source_files.tsv` | — | generated with it: candidate intervals that cite a source file name, or lie between two citations of one file |

## Conventions adopted from RAC1

- **One line, one fact, with a header comment that says who reads it.**
- **Comments carry the reason**, not just the value: a flag line names the
  function it was measured for, as `file_cflags.txt` does.
- **A handwritten-assembly list is configuration, not a report.** RAC1 keeps
  `handwritten_asm.txt`; we keep `handwritten_asm.tsv` with the class of the
  blocker, so the next wave does not re-try a C form that cannot work.
- **Generated tables say so** and are regenerated by a named tool; `--check`
  in the gates compares them byte for byte.

## Not adopted, and why

- **`splat.yaml`**: splat drives the disassembly split. Our boot and level
  modules are already pinned with complete assembly baselines
  (`tools/level_program_gate.py`), so a splat config would be a second,
  unverified description of the same bytes.
- **`names.tsv` / `names_local.tsv` layering**: useful once inferred names
  outnumber measured ones. Today every accepted body's name comes from the
  retail symbol table, so a second naming layer would have nothing to hold.
- **`strings.tsv` / `strings.json`**: worth adding when the level work starts
  naming string-referencing functions by content rather than by address.

## levels/bodies.tsv schema

```
module	offset	size	source
```

One row per placement: where a body sits and which source fills it. The
measured facts of a source — its two hashes, its compiler profile and its
assembler — belong to the source, not to the placement, so they are written
once per source in `levels/body_sources.tsv`:

```
source	source_sha256_lf	object_sha256	profile	as
```

A source carried by hundreds of placements therefore costs one row in the
source table, and the placement table stays small enough for the repository's
targeted size guards on tracked files.

`levels/local_link_symbols.tsv` is an opt-in table for a compiler-generated
`__muldi3` call that resolves to a measured helper in the same module. Each row
pins the module, accepted C source, compiled object SHA, helper address, size,
helper SHA and four call-site offsets. The level gate verifies the helper and
object again before linking; it does not infer a call target from the retail
caller bytes. Sources without a qualified row keep strict symbol resolution.

- `offset` is hexadecimal (`0x00000100`); `size` is decimal bytes and a
  multiple of four.
- `source` is repository-relative. A source lives in its module's directory
  (`src/levels/frontend/`, `src/levels/01_pokitaru/` ... `src/levels/24_treehouse/`)
  when all of its placements are in that module, and in `src/levels/shared/`
  when they span several modules; LEVEL_21.REL placements count as
  LEVEL_15.REL's. `python tools/level_source_layout.py --apply` restores this
  layout (see `src/levels/README.md`).
- `profile` is `pinned` (the `compiler-no-pad-20261015` cc1), `gnu-ee-trial`
  (the same GNU EE build without the increasing-callee-saved patch, passed as
  `--extra-cc1 gnu-ee-trial=PATH`), `gnu-ee-trial-divpad` (the same build
  with the upstream save order and the R5900 division padding, passed as
  `--extra-cc1 gnu-ee-trial-divpad=PATH`),
  `gnu-ee-trial-divpad-blockmove` (an opt-in, SHA-pinned copy of that profile
  with the 32-byte block-move loop count corrected, passed as
  `--extra-cc1 gnu-ee-trial-divpad-blockmove=PATH`), or one of the two Sony EE-GCC
  builds the boot campaign already pins, `sdk991111` and `sdk991111sync`
  (`--extra-cc1 sdk991111=PATH`, `--extra-cc1 sdk991111sync=PATH`). `as` is
  the pinned GNU `gnu-ee-trial-20261015` assembler for every row.
- An external name must be a module import, a module export, or a name that
  carries its address (`func_<addr>` / `D_<addr>`). The gate deliberately does
  not resolve a name from the retail bytes it is proving; a source that needs
  that fails with the unresolved names.
- `object_sha256` covers the whole object file, so it depends on the source
  basename (the ELF file symbol). Distinct lot sources that share a basename
  are stored with a lot or module suffix; their object hash is the gate's
  measurement for the stored name, not the lot's original hash.
- `tools/level_c_gate.py --refresh-bodies` recomputes both hash columns of the
  source table after a full pass. An ordinary run verifies them and fails on a
  stale row.
- A placement must name a source the source table declares, and a source the
  table declares must be carried by at least one placement; the gate refuses
  an orphan on either side.
- Placements must not overlap within a module. The `0x100` row may overlap the
  already counted shared body because the gate checks the two byte strings are
  identical before accepting the overlap.
