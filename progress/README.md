# Scoped progress snapshot

[`status.json`](status.json) is generated by [`tools/progress_status.py`](../tools/progress_status.py)
after the private boot and level-program gates pass. It records **693 accepted
boot C functions (88,948 bytes) in the 498,900-byte boot `.text`**, **one 476-byte C
function in `FRONTEND.REL`**, plus **two shared C functions (8 + 72 bytes)
at twenty numbered level placements** and, counted separately, the
**57,345 accepted level-body placements**
(6,840,572 placement bytes carried by 42,468 sources, 5,786,384 distinct-source
bytes; **700,772 bytes in 5,075 relocation-masked shape units** when each shape
is counted once, at its largest per-module multiplicity, like the level
denominator). The shared pair counts as two authored functions, not forty
independent matches, and the level bodies are a scope of their own: one
authored source can carry many placements, and the address-variant copies of
one function in several levels are separate sources of one masked shape. Two other exact C shapes remain
provisional controls. `FRONTEND.REL` and `LEVEL_01.REL` have exact complete-file assembly
replacement and measured relocated-image baselines. Their original non-code
bytes are still inputs, and assembly equality is not C progress.

The 21 level code intervals total 36,341,888 **bytes by placement**. They are
candidate code intervals, not verified function sizes or unique game code.
`LEVEL_15.REL` and `LEVEL_21.REL` already have identical complete interval
hashes; smaller shared functions may occur elsewhere. `overall_percent` is
therefore `null`. The only percentage in the snapshot is explicitly scoped to
the boot `.text`: 88,948 / 498,900 bytes (17.83%).
The [function-boundary and deduplication audit](../docs/research/level-function-inventory.md)
now records 124,356 possible entry intervals, 74,051 stronger bounded
candidates and an exact-duplicate upper bound of 33,168,892 candidate bytes.
Relocation-masked groups remain review leads, not counted progress.
An independent R5900 Ghidra pass agrees with **91,350** of those candidate
boundaries. The data-target and closed local-callgraph checks retain **2,415
shared template leads**, including one 32,796-byte body across all twenty numbered
levels. The [audit guide](../docs/research/level-function-inventory.md) explains why
these are useful deduplication worklists but still not an exact unique-code
denominator.
The optional Ghidra body-range pass flags **1,590** candidate starts inside
another body; **1,209** also have a direct branch or jump from that same body.
A full-module pass classifies all 1,590 as review leads, including **21**
newly called function entries and **229** contiguous cases without a recovered
indirect reference. These remain candidate evidence, not counted C progress.
The split-body audit selects **6,245** corroborated segments inside **3,729**
oversized candidate intervals, leaving 294,836 surrounding body bytes unique.
Its **23,471,984-byte** result, including conditional target-graph matches
for zero-filled local data and placement-checked partial families, is a
conditional deduplication scenario, not a verified unique-code denominator.
The [switch-body review](../docs/research/level-function-inventory.md#contiguous-switch-body-review)
identifies 1,117 contiguous function placements before data and call checks.
An [optimistic masked-shape audit](../docs/research/level-function-inventory.md#optimistic-relocation-masked-shape-scenario)
also measures **5,756,360 candidate bytes** when identical masked bodies are
grouped across levels while repeated bodies inside one level stay separate.
That is a useful aggressive research scenario, not an accepted progress total.
An additional [context/data review](../docs/research/level-function-inventory.md#repeated-shapes-with-code-context-and-data-anchors)
retains 5,631 repeated-shape families, including reviewed split segments and
62 switch-body families, after global collision and final-callee checks and
gives a **16,857,360-byte conditional
scenario**. This too remains a structural worklist, not counted C progress.
The separate [site-paired role review](../docs/research/level-function-inventory.md#site-paired-code-role-review)
retains 141,319 conditional pairs after global collision, code-role and
dependency checks, giving a **10,088,660-byte normalized-code scenario**.
Its 13 selected reference modules reproduce the savings measured with all 20.
Variant callees may have different source; this is not a qualified denominator
or counted C progress.

The Ghidra cross-check also requires private metadata exports; its
[reproduction guide](../tools/ghidra/README.md) gives the command. Progress
`--write` requires the ignored private gate receipts. CI can run `--check`
without game data; it detects drift in the committed catalogues, accepted C
source and reported evidence. CI does not repeat the proprietary-tool builds.

This scoped snapshot is **not an objdiff v2 report**. A separate
[`tools/gen_progress_report.py`](../tools/gen_progress_report.py) builds the
objdiff v2 report for [ByteMatch](https://bytematch.dev/OpenRAC/rac5-sm-decomp)
from this snapshot and the public shape map
[`config/levels/shape_units.tsv`](../config/levels/shape_units.tsv), written with
[`config/levels/accepted_shape_summary.json`](../config/levels/accepted_shape_summary.json)
by [`tools/level_accepted_shapes.py`](../tools/level_accepted_shapes.py). On
successful pushes to `master`, the progress workflow uploads
`SCUS_976.15_report/report.json`; ByteMatch reads that artifact as its progress
graph. Its denominator combines **498,900 measured boot `.text` bytes** and the
**5,756,360 optimistically deduplicated candidate bytes** of the 20 retained
level modules, `FRONTEND.REL` included, for **6,255,260 provisional code
bytes**. The numerator is **792,060 accepted C bytes**: 88,948 in boot and
703,112 in the level modules. A level candidate unit counts as matched when
accepted C reproduces all of its bytes at its own placement, once per
relocation-masked shape at its largest multiplicity in one module; accepted
bytes outside every candidate unit (3,440) count where they lie. The
address-variant copies of one function in several levels are separate sources
but one masked shape, so they count once; counting by source
(5,786,384 bytes) credited them up to twenty times against a denominator that
counts them once. The site rounds the resulting approximately
**12.6623%** to **12.66%**. Until 2026-11-11 the report also added the
162,944 frontend candidate bytes a second time to the denominator and credited
the shared and frontend C functions, already in the placement table, twice.

ByteMatch's map draws one tile per report unit, grouped in folders by the unit
names, sized by code bytes and coloured matched, in progress or not started.
The units follow the source tree. `boot/<symbol>` tiles are the 1,315
candidate boot code intervals; an accepted body counts its body bytes, and its
linker alignment joins the bytes outside every interval in
`boot/_unlabeled_code_and_padding`. `levels/<module directory>/<MODULE_OFFSET>`
and `levels/shared/<MODULE_OFFSET>` tiles are the 9,388 relocation-masked level
shapes, placed like their sources in [`src/levels/`](../src/levels/README.md): a
shape found in several modules sits in `shared/`, any other in its module's
directory. Each module also has a `code_without_function_bounds` tile for its
candidate code outside every candidate unit and, when accepted C lies there, an
`accepted_code_outside_candidate_units` tile. Matched level tiles link to their
source. The categories partition the same tiles: boot, the level modules, each
module's own directory and the shared code.

ByteMatch's function counts use the same units as its code bytes:
**5,809 of 12,814 candidate functions**, from the 1,315 candidate boot code
intervals (693 accepted) and the 11,499 relocation-masked level shape units of
the 20 measured modules, each shape counted once at its largest per-module
multiplicity (5,116 covered by accepted C). These are candidate functions, not
a reviewed function catalogue: a masked shape can still cover different data
roles or C definitions, and corrected boundaries can change both counts.

The dashboard's level category says **each candidate shape counted once**: the
denominator is an optimistic masked-shape estimate. It can rise when a
presumed shared shape splits into distinct functions, or change as boundaries
are corrected. It is not a qualified unique-code size or a verified game-wide
matching percentage. The `overall_percent: null` and
`bytematch_objdiff_ready: false` fields above remain the authoritative
qualification status. Regenerate this separate artifact from public metadata
with `python tools/gen_progress_report.py`; CI checks it without uploading
private game data. The separate
[`tools/bytematch_estimate.py`](../tools/bytematch_estimate.py) still validates
the labelled estimate used by the scoped status snapshot.
